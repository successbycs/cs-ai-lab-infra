# Project-support foundation

This repository owns host operations, reusable templates, and the inventory—not product source, assets, or deployment definitions. The machine-readable contract is [the registry schema](../projects/project-registry.schema.json); the safe undeployed examples are [the registry](../projects/registry.example.json) and [static-web template](../templates/static-web/README.md).

Project assets are project-owned: retain source design exports, original assets, generated output, and licence/attribution records in that product repository or its chosen product storage. Do not create a mutable shared asset volume across products.

Secrets are injected at runtime from a mode-0600 ignored per-project file, referenced by absolute path in the registry but never copied into it. Existing OpenWorker evidence proves loopback health/UI only; its repository and current runtime configuration have not established a suitable general secret store. Before a migration, separately verify its encrypted-at-rest capability, runtime injection path, backup/restore semantics, rotation/revocation, and rollback. The prior Penpot-key exposure requires rotation evidence; no key was read, copied, or regenerated here.

Recoverable state is declared per project in the registry. Keep an off-device copy according to its backup plan and run a scoped restore test into a non-live target before claiming recovery. Existing backup/restore actions remain governed by their approved operation boundaries.

## Capacity evidence and rollout gate

T480 evidence captured 2026-09-12 NZST: Windows C: 16.9 GiB free of 235.6 GiB (7.2%); Windows had 15.84 GiB RAM with 2.95 GiB free at the snapshot and 45% CPU. The active WSL filesystem simultaneously reported 900 GiB free and 6.4 GiB available memory of 9.7 GiB. That virtual free space is not physical C: capacity; its VHDX host-file growth must be measured before deploying anything persistent. Penpot was healthy but already using about 1.67 GiB across its six containers. The existing lab, Ollama, Penpot and OpenWorker were healthy; no router was inspected, restarted, or redirected. This is not sustained capacity proof: owner action is to collect governed `performance_diagnostics`, `storage`, `lab_health`, and `penpot_resource_report` samples during representative work over at least one normal workday, then set project limits from the observed minimum headroom.

The hardware operation found two occupied 8 GiB DDR4-2400 SODIMMs (one Samsung and one Crucial) and an Intel SSDPEKKF256G8L 256 GB SSD. It resolved the registered WSL `ext4.vhdx` host file at 57.17 GiB on C:; Docker's root is `/var/lib/docker` inside that WSL filesystem. This confirms that Docker growth consumes the already constrained physical C: drive even though Linux reports 900 GiB free. Recommended next steps: do not free space automatically; obtain a compatible M.2 2280 NVMe replacement/migration plan after confirming the T480 storage slot, and use a matched DDR4-2400 SODIMM kit if increasing RAM (the current two slots are occupied). With the current 7.2% C: headroom and one high-use memory sample, do not deploy a new service yet.
